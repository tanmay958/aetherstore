        What this is

        An inverted index, a segment format, a query coordinator, a Kafka indexer, a compactor and a streaming prediction pipeline, none of which use a search or serving library. The only runtime dependency of the engine is numpy.

        Why a query costs what it costs

        Documents live in immutable segments in object storage. Opening one costs two range reads, for a footer and a small header block, and both are cached forever because a segment can never change. After that, each distinct term costs a dictionary read and a postings read per segment that survives pruning.

        That is why a warm instance still spends requests, and why it should: caching removes the cost of opening, paid once, not the cost of reading, paid per term. It is also why the index is compacted. Merging 100 segments into 10 took a cold query from 124 requests to 15.

        Why prediction needs no coordination

        Events are published to Kafka keyed by session id, so every event for a session lands on one partition, and Kafka gives each partition to exactly one consumer in a group. One replica therefore sees a session's whole history and can hold its state in a plain dictionary: no Redis, no locks, no consensus. Single-writer safety was inherited from the log rather than built.

        Take the key away and it collapses. Events round-robin, every replica sees a fragment of every session, and the state has to move somewhere shared.

        Where things run

        This page is on Cloudflare Pages. The API is on Cloud Run, which scales to zero, so the first request after an idle period pays about half a second to start. The index and the model are on Cloudflare R2. The three-replica streaming predictor and its broker stay on a laptop, because a consumer that scales to zero does not idle cheaply, it falls behind.
